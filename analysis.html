1. The Files-app problem

Unlike WhatsApp (one app group) or Photos (one CameraRollDomain), the iPhone Files app aggregates storage that lives across four separate backup domains. A tool that only extracts one domain will show you a fragment of what you actually see on the phone.

Gap identified: every existing tool is a generic single-domain extractor (you pick the domain) or a photo/WhatsApp-specialised tool. None reconstructs the user-visible Files tree across all four domains. That is the value our project adds.

3. The shared algorithm (common pattern)

Every tool, regardless of language, converges on the same 4 steps:

  1. Open Manifest.db (read-only), read the Files table: fileID, domain, relativePath, flags, file.
  2. Map flags to a filesystem type: 1=file, 2=directory, 4=symlink, 10=hardlink.
  3. Resolve the payload at <backup>/<fileID[:2]>/<fileID>.
  4. Reconstruct the output tree from domain / namespace / relativePath, then copy each payload there (restoring dates from the binary plist).

For the Files app specifically, you then aggregate the four domains under one output root.

Metadata (the tricky part)

The file column is a binary plist of NSKeyed-archiver objects. The useful values live in $objects[1]: Birth, LastModified, Size, and Target (a UID reference for symlinks). All timestamps are in Apple epoch (seconds since 2001-01-01), so add 978307200 to get Unix.

correct

plistlib.loads(blob, fmt=FMT_BINARY) — the right approach (used by greatvovan). Some tools skip metadata entirely (conorarmstrong) or do a fragile byte-scan (the photo tool's first cut).

4. Weaknesses in the existing tools

  • serialSerial copy. Nearly all copy one file at a time (conorarmstrong, greatvovan, richinfante). For a multi-GB Files tree this is slow.
  • no resumeNo incremental resume or dedupe. A re-run re-copies everything; overlapping domains re-copy shared bytes.
  • no empty dirsDirectory entries dropped. Most tools skip flags==2, so genuinely empty folders are lost (unixzii, conorarmstrong).
  • dir mtimeDirectory mtime set too early. greatvovan correctly postpones it; the others would reset the dir time after children are written.
  • single domainNo Files-app awareness. None aggregate the four Files domains into one readable tree.
  • symlink copySymlinks treated as files (default) — fine for content, but the target reference is lost.

6. Verified behaviour

Validated against a synthetic multi-domain backup (4 domains, files + a directory entry + a hardlink-type entry + duplicate filenames + two .Trash folders):

  • All 4 Files domains aggregated and extracted.
  • Full path preservation incl. File Provider Storage/ + .Trash.
  • 9 files byte-identical to source payloads (SHA-256 content match).
  • Creation/modification dates restored correctly (Apple epoch handled once).
  • Duplicate report.pdf disambiguated across folders.
  • --link creates true hardlinks (same inode as source).
  • --local-only restricts to the two on-device domains; --flat drops the labelled top folder.
